Why memory stays flat

  • One audio graph. A single shared AudioContext; each clip disconnects the previous source.
  • Sprite sheets, not frames. Walk cycles change an SVG viewBox; sheets went 1.96 MB → 191 KB.
  • Paused when hidden. Kept routes park their animation loops and timers.
  • Light pages. 471–859 DOM nodes; 12–16 MB heap.

Security

Every request passes six gates

Each gate stops a different attack. The last one is in the database itself, so a bug in the app still cannot expose another child's data.

Private audio linksHMAC-signed, valid 30 minutes, compared in constant time; never stored.
No identity to partnersThe voice service gets a pseudonym, never account id, name or email.
Request forgery blockedAudio URLs from the voice service must match a host allow-list.
No script injectionLearner or network text is never written as HTML.
No open redirectsSign-in ignores next; return paths reject // and \.
Prompt injectionChildren's answers are fenced as data; attempts are flagged in scoring.
Patched dependenciesNext.js 16.4.0 → 16.4.2 (critical advisories); nodemailer → 10.2.1.
Secrets server-onlyThe database secret-key client refuses to run in a browser.

Network and storage

  • Per learner: 5 Mbps min, 10 recommended. First visit 1.5–3 MB per page, then mostly cached.
  • Class of 30: about 50–90 MB when everyone opens a page the first time.
  • Storage: nothing installed; browser cache only.

Why no GPU is needed

  • All graphics are SVG and CSS animation on the browser's compositor: no WebGL, canvas or 3D.
  • AI and speech run in the cloud, not on the device; servers need no GPU either.
  • Measured: 12–16 MB JavaScript memory and 471–859 elements per page.

Infrastructure

Recommended server configurations

The app keeps no state on the server, so it grows by adding identical nodes. One Next.js process used about 100 MB in our test.

A self-hosted node (Ubuntu)

  1. Ubuntu 24.04 LTS with Node.js 22 LTS (Next.js 16 needs 20.9+).
  2. next build then next start under systemd or PM2; one process per 1–2 vCPU, 300–500 MB each under load.
  3. nginx in front: HTTP/2, Brotli, TLS; cache /_next/static and /assets for a year.
  4. A CDN in front for static files and the 1.4 GB voice library.

Before growing past one node

  • Shared rate limiter: today limits live in each server's memory.
  • Queue AI scoring and answers for whole-class bursts.
  • Size the voice service with the AI team: the slowest dependency.
  • Load test, error tracking and uptime monitoring.

Q&A

Questions a technical lead will ask

Can it handle 100,000 learners at once?

The architecture allows it: static files on a CDN, lessons in the browser, stateless server routes. The limits will be database connections, AI rate limits and the single voice-service host. Until a load test proves it, 100,000 is a design target.

What happens when the AI or voice service is down?

Lessons keep working from the pre-recorded library. Questions fail with a kind line from the tutor, late audio falls back to text, and scoring retries when the AI is busy.

How do we know there is no memory leak?

Heap sampled every 10 s for 60 s after garbage collection: flat at 12.1 MB after loading, listeners steady at 401. A 30–60 minute soak test through several missions is next.

Do learners need a graphics card?

No. Everything is SVG and CSS animation; AI and speech run in the cloud. Integrated graphics on any 2018+ laptop is enough.

Is it safe for children's data?

Each child can reach only their own rows, enforced in the database. Recordings and answer audio are never stored, partners see a pseudonym and keys never leave the server. Close the three "Fix" items before a large rollout.

Can we move off Vercel?

Yes: standard next build / next start on any Node.js 20.9+ server, with a CDN in front.

How does quality hold with several developers pushing daily?

50 unit test files, 26 end-to-end specs, viewport checks at four sizes, migrations tested on in-memory Postgres, git hooks on every commit and push, and main only through reviewed pull requests.
